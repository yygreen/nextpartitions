# Installer directory module

Built to drop into the live nextpartitions.com app. The live site is a Lovable project using **TanStack Start (React, server-rendered) with a Supabase backend**, so this module uses the same stack. Every database object is prefixed `dir_` so nothing collides with the existing schema.

## The rules the database enforces

- **Customer details stay hidden** from installers until the customer has chosen that installer **and** paid for the partitions order. `released_at` is set only by a trigger; reversing the payment hides them again.
- Before release, installers see a **blind job packet** only: scope, drawings, city/ZIP, delivery window, a job reference.
- Installers can price jobs they were invited to, message **through Next Partitions**, and edit their own profile text and rate card. They can't change their status, approval, tracked phone, or any job field except install date and status (scheduled → installed) after release. An install date can't be before delivery.
- The public site reads three views only (`dir_public_installers`, `dir_public_rate_cards`, `dir_public_reviews`): approved installers, published reviews and passed checks, with no legal names, documents or internal notes.
- **Approval needs five passed checks**: insurance, business or city registration, references, the timed test job (`response_test`) and the listing agreement. Nobody can approve around them from the portal.
- **Labels are tiered.** Listing an installer (status `approved`, allowed only once the five checks pass) makes their profile public with the **Verified** label and starts job requests. Signing off their first job passes the `completed_job` check and the label becomes **Approved** (the public view's `installs` goes from 0 to 1). Established and Top rated follow from installs and reviews.
- **Customers reach their quote only through a secret link** (`dir_job_quotes.token`). Installers can't read that table, so they never see the link or the partitions prices. Test jobs have no quote.
- Reply time is measured automatically (`responded_at` is stamped on the first answer) and shown as a median on the profile.

## Running the pages locally

```sh
cd app
npm install
npm run dev        # http://localhost:3000/service-area/texas (sample data, marked noindex)
npm test           # estimate maths, portal stages and dates
npm run typecheck
```

Set `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` (see `.env.example`) to read real data instead of the fictional sample installers. The portal (`/portal/`) reads `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` in the browser; giving installers a login also needs `SUPABASE_SERVICE_ROLE_KEY` on the server (never a `VITE_` variable).

## Job routing: what runs where

- `dir_route_job(job)` invites up to 3 installers when a quote request with drawings becomes a job. Call it from the server (service role) or as an admin.
- `dir_sweep_jobs()` runs every 15 minutes (pg_cron, scheduled by the migration if the extension is on). It closes price windows, widens the search once to 75 mi when nobody priced, flags jobs for the job coordinator (`needs_attention`) and sends 20-hour reminders.
- `dir_invite_installer(job, installer)` is the job coordinator's "invite by hand".
- Every event that should send an email or update the CRM lands in `dir_outbox` (`job_invite`, `invite_reminder`, `invite_answered`, `prices_ready`, `search_widened`, `no_prices`, `installer_chosen`, `job_released`, `job_status`, `review_request`). The email worker (`supabase/functions/dir-outbox`) calls `dir_outbox_claim()`, reads each row with `dir_outbox_context(id)`, sends the emails, then `dir_outbox_done(id)`; a failed row is retried on the next run, up to 5 attempts. Resend is wired in as the first email service (not chosen yet; another one is a small function in `index.ts`); the CRM update isn't built until the CRM is chosen.
- Jobs and installers get `lat`/`lng` from their ZIP code automatically (`dir_zip_centroids`), unless a location is given. A ZIP that isn't in the data leaves the job without a location, and routing flags it for the job coordinator. Distances are straight-line × 1.2 until Google Routes is connected.

## For Marc: how to merge it

1. Lovable projects sync two-way with GitHub. The simplest route is to **add us as a collaborator on the project's GitHub repo**; we open a pull request there and Lovable picks it up on merge. No Lovable seat needed.
2. Run the migration on the Supabase project (or let Lovable apply it from `supabase/migrations/`).
3. Map `dir_admins` to the site's existing admin role, if there is one.
4. Installer portal logins reuse Supabase Auth: an installer is a normal user linked through `dir_installers.user_id`. The coordinator gives the login from the portal (Installers tab); the installer gets Supabase's invite email and then signs in with an emailed link (no password, and nobody can sign up from the login page). Add `https://nextpartitions.com/portal/` to the project's Auth redirect URLs.
5. Turn on pg_cron (Database → Extensions) before running the migrations, so the 15-minute sweep is scheduled.

## Open decisions that may change the schema

- Payment collection on the installer's behalf and the single checkout: needs the lawyer and CPA (adds payout fields).
- Taking partitions payments on the quote page: today it records PO, card-link or bank-transfer and the job coordinator follows up. Paying by card on the page needs the site's payment provider (ask Marc); marking the job paid would then be automatic.
- How `quote_request_ref` links to the existing quote requests: needs a look at the live schema.
- Rate cards hold a low and high per-stall price; estimates use the midpoint. If installers agree a single price per stall, set low = high.
- Whether site-measure visits release the site address early (an extra release stage).
- Rate card changes go live straight away (the prototype says Next Partitions checks them within 1 business day). Each invite keeps the estimate from the rates at the time, so price checks aren't affected; add a review step if Abe wants one.
